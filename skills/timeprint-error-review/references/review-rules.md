# 日报与状态规则

## 数据口径

采集器扫描目标日及相邻日期目录，处理客户端旧版时区差异。结构化日志用 `created_at_ms` 严格筛选目标日；旧式日志或无合法事件时间的记录按 COS 上传时间筛选，并标 `timeBasis=upload`，不能称为确切事件发生时间。未被采样、超过大小限制、延迟上传而尚未出现的日志都可能遗漏。没有周期扫描或游标，不承诺未来迟到日志被本次覆盖；需要时手动重跑对应日期，新日报会保留为新版本。

日报字段见 web `src/lib/error-reviews/contracts.ts`。采集结果不是完整统计：listed 是三天目录元数据数，downloaded 是正文读取数，evidence 是窗口内且去重后的样本数；这些数字不能混用。设备计数仅针对有设备 HMAC 的样本。iOS 与 Android 的标识不能互相去重。`listingComplete=false` 是采集缺口，不是零错误。

每个 finding 应简短包含：标题、P0–P3、confirmed/suspected、证据结论、待验证原因、下一步。confirmed 只表示该项结论有证据支持，不意味着已证明整个故障根因。排优先级时参考版本、独立设备、前后台、恢复结果和用户影响，不以日志条数替代用户数。

建议 P0：有可靠证据的广泛启动阻断/数据丢失；P1：新启动崩溃或核心功能最终失败；P2：局部机型故障或可恢复错误；P3：低影响已知告警。样本有限时不要把“广泛”写成事实。对疑似黑屏串联 no-frame、recovery_exhausted、provider reset、first-frame 等阶段；runtime 详细轨迹不在 error folder 时明确缺证，需用户授权扩展采集范围。

## 状态维护

平台“问题台账 → 维护 / 历史”提供：

| 状态 | 进入条件 |
|---|---|
| 新发现 | 日报首次登记该指纹 |
| 待定位 | 分配负责人，记录排查计划 |
| 已定位 | 有源码/日志/复现证据，说明原因 |
| 已修复待发布 | 填修复版本及建议的 commit/PR HTTPS 链接 |
| 已发布待验证 | 修复版本实际发布，说明验证计划 |
| 已关闭 | 填修复版本，记录真机/新版本样本等验证依据；不能只凭某日没有日志 |
| 已忽略 | 明确记录不处理原因，保留证据 |

允许新发现直接进入已定位。排查中可忽略；已修复、验证中、已关闭、已忽略可回到待定位。每次维护可改负责人、修复版本/链接，并且必填原因。平台用版本号检查并发修改，冲突时刷新重试；每次变更记录操作者、前后状态和时间。同日多次 review 的观察记录不应相加视为独立样本。

复发的关闭问题在日报中提醒核对修复版本与事件时间。平台不自动重开或关闭，技能默认仅给出状态建议。
